# Memory Pool 진화: GPU Compacting

> 3단계 시행착오를 거쳐 가장 단순하고 효율적인 방법 도달

---

## 핵심 내용

- **1단계 CPU Defrag**: CPU가 블록 재배치 계획 → GPU 메모리 복사 → **프레임 스파이크** → 비효율
- **2단계 Paging**: 페이지 테이블로 불연속 블록 관리 → **복잡도 증가, 이점 미미** → 폐기
- **3단계 GPU Compacting (최종 채택)**: 시뮬레이션 CS에서 **InterlockedAdd로 alive index 재기록** → 자동 컴팩팅

## WHY

- 핵심 인사이트: 시뮬레이션 CS가 **이미 모든 alive 파티클을 순회**하고 있음
- alive index를 InterlockedAdd로 연속 기록하면 **별도 패스 없이** 컴팩팅 완료
- 파티클 데이터 자체는 이동하지 않음 — **alive index만 재기록**
- 추가 비용: **제로** (별도 디스패치 불필요, 시뮬레이션과 동시 수행)

---

## 시각화 레이아웃 — 3단계 진화 과정 (세로 타임라인)

```
┌─── 1단계: CPU Defragmentation ──────────────────────────────────┐
│ 방법: CPU가 블록 재배치 계획 → GPU에 복사 명령                  │
│                                                                  │
│ [A][_][B][_][C] ──CPU계획──▶ [A][B][C][_][_]                   │
│                    ↑                                             │
│ 문제: GPU 메모리 블록 복사 비용 큼 → 프레임 스파이크!           │
│ 결과: ✗ 비효율                                                  │
└──────────────────────────────────────────────────────────────────┘
                                ▼
┌─── 2단계: Paging ───────────────────────────────────────────────┐
│ 방법: 페이지 테이블로 불연속 블록을 논리적으로 연속 관리        │
│                                                                  │
│ 물리: [A][_][A][_][A]   논리: [A][A][A] (페이지 테이블 매핑)   │
│                                                                  │
│ 문제: 인덱싱 복잡도 증가, 관리 오버헤드 대비 이점 미미          │
│ 결과: ✗ 폐기                                                    │
└──────────────────────────────────────────────────────────────────┘
                                ▼
┌─── 3단계: GPU Compacting (최종 채택) ───────────────────────────┐
│ 핵심 인사이트: 시뮬레이션 CS가 이미 모든 alive 파티클을 순회!   │
│                                                                  │
│ Read Alive:  [5, _, 8, _, _, 2, 7, _]  (구멍 있음)             │
│                    ▼ 시뮬레이션 + InterlockedAdd                │
│ Write Alive: [5, 8, 2, 7, _, _, _, _]  (연속! 자동 컴팩팅)     │
│                                                                  │
│ 파티클 데이터 자체는 이동 안 함 — alive index만 재기록          │
│ 추가 비용: 제로 (별도 패스 없음, 시뮬레이션과 동시 수행)        │
│ 결과: ✓ 가장 단순하고 효율적                                    │
└──────────────────────────────────────────────────────────────────┘
```

- **3개 박스를 세로로** 배치, 각 단계를 **아래쪽 화살표**로 연결
- 1단계: **빨간 테두리** + ✗ 아이콘 (비효율)
- 2단계: **주황 테두리** + ✗ 아이콘 (폐기)
- 3단계: **초록 테두리 + 굵은 강조** + ✓ 아이콘 (최종 채택)
- 3단계 내부: Read Alive → Write Alive 변환을 **Before/After** 배열로 시각화
- 구멍(_)이 사라지고 연속으로 재기록되는 과정을 **색상 이동 화살표**로 표현
- 하단에 "추가 비용: **제로**" 대형 텍스트 강조
